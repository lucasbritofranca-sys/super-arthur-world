# ADR-005: Transactional local saves and revision-based cloud synchronization

## Status
Accepted

## Date
2026-10-11

## Context
Six guest/account slots must survive checkpoint/reopen, retain spent lives and apply scoped Game Over penalties. Explicit device conflicts cannot silently merge or resurrect a reset. There is no requirement for a server-authoritative competitive game.

## Decision
Use IndexedDB transactional snapshots/outbox keyed by scope and slot. Store a bounded validated campaign JSONB snapshot in one Supabase game_saves table with typed owner/slot/revision/mutation/time columns. Enforce owner RLS and direct conditional revision updates; no unconditional upsert. Tombstones preserve revisions across deletion. Serialize one immutable in-flight request per slot and latest desired successor. Keep life balance outside the restart snapshot; ordinary death writes current lives minus one without committing tentative items. Game Over writes one reset transaction before Continue.

## Alternatives Considered
### localStorage and latest-timestamp wins
Less code, but lacks snapshot/outbox transaction and violates chosen explicit-conflict/reset behavior.
### Progression side-tables/event history/RPC server
Can support richer queries/history, but this game reads six whole slots and needs no leaderboards. Adds avoidable components. A narrow table trigger validates revisions/schema, not a custom server/RPC write API.

## Consequences
### Positive
Atomic local continuation, owner-private cloud saves and simple inspectable conflict semantics.
### Negative
Conflict UI, failure statuses and outbox acknowledgement logic are required.
### Risks
In-flight old save may finish after local reset. Acknowledge its revision without restoring its payload, then send the reset; unknown remote changes always require choice. Local quota failure cannot claim durability. Keep account namespace invisible after logout.

## Implementation Notes
Maximum payload 256KiB, schema version 1. RLS SELECT/INSERT/UPDATE ownership; no DELETE or anon privileges. DB trigger enforces monotonic revision and stable owner/slot. Tests cover two clients, lost acknowledgements, reset/deletion, duplicate death/reward and real unauthorized operations.
